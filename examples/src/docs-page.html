Rate limiting

The rate detector scores clients that send too many requests in a sliding window. It never blocks on its own: it reports a score, and the policy decides.

Overview

Every request is counted against a key, by default the client address after trusted proxies are removed. When the count in the window passes the limit, the detector reports a score that grows with how far over the limit the client is.

{{icon:info}}
Note
Counts live in the configured store. With the memory store each node counts on its own, so a client spread over six nodes gets six times the limit.

Quick start

Add the detector to the pipeline and give it a limit:

server.tsts
import { createBotHandler, rate } from "bothandlerjs";

const bots = createBotHandler({
  detectors: [rate({ limit: 30, windowSeconds: 60, paths: ["/api/login"] })],
  policy: { challengeAt: 40, blockAt: 80 },
});

app.use(bots.middleware()); // Express; see Adapters for the others
{{icon:success}}
Tip
Start with the policy in monitor mode for a day. The dashboard shows what would have been challenged, and you can tune the limit before anything is blocked.

Configuration

All options, with their defaults. Unknown keys are rejected at start-up rather than ignored.

OptionTypeDefaultMeaning
limitnumber60Requests allowed per window before scoring starts.
windowSecondsnumber60Length of the sliding window.
pathsstring[]["*"]Which paths count. * matches one segment.
key(ctx) => stringclient IPWhat is counted, e.g. an API key or a session.
maxScorenumber100The cap; a policy threshold above it can never fire.

Windows and bursts

The window slides in one-second steps, so a burst at the edge of a minute is counted against the next minute too. Two settings change how bursts feel:

  • A short window (10–30 s) catches scripted bursts quickly but is noisy for humans who double-click.
  • A long window (5–15 min) is forgiving and catches slow scrapers that stay just under a per-minute limit.

Choosing the key

Counting by address treats a whole office behind one NAT as one client. For signed-in traffic, count by user instead:

ts
rate({
  key: (ctx) => ctx.user?.id ?? ctx.ip,
  limit: 120,
});

What the client sees

The detector itself sends nothing. When the policy challenges or blocks, the response carries a Retry-After header and this body:

429 Too Many Requestsjson
{
  "error": "rate_limited",
  "retryAfterSeconds": 23,
  "requestId": "req_8f2c41a7"
}

Reloading

Limits, windows and paths reload without a restart. Changing the store does not: the old counts would be lost silently, so the reload reports it instead.

{{icon:warning}}
Caution
Lowering windowSeconds on a live node keeps the counts already collected, so the first window after the reload can over-count. Reload during quiet hours.
{{icon:error}}
Important
A threshold above maxScore is a policy that can never fire. bothandler check fails on it; do not silence that check.

Troubleshooting

Every client is being limited
The node probably sees the load balancer's address. Add it to trustedProxies so the real client address is read from X-Forwarded-For.
Counts reset every few minutes
With the memory store, a restart or a deploy clears the counts. Use the Redis store for counts that survive.
The dashboard shows no rate scores
Check that paths matches: /api/* matches /api/login but not /api/v2/login. Use /api/** for any depth.
